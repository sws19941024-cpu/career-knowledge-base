Example - Wrong Data Investigation Case
Business User reported that a VBA report showed an incorrect allocation total and failed business validation.
User Reported Issue
Expected: 10,000 Units Actual: 9,650 Units Difference: 350 Units Missing
Investigation Path
VBA Output → Data Dump → Dataiku Dataset → MicroStrategy SQL

The investigation started from the final VBA report because that was what business users actually saw.

Step 1 - VBA Validation
  • Confirmed VBA calculations were producing expected totals
  • Checked report filters and parameters
  • Verified export logic

No issue found.

Step 2 - Data Dump Validation
  • Compared VBA output against source dump file
  • Verified row counts
  • Verified affected products existed in dump data

Missing records already existed before VBA processing.

Step 3 - Dataiku Dataset Validation
  • Compared row counts between datasets
  • Validated joins and mappings
  • Checked recent workflow changes

No records missing at dataset level.

Step 4 - SQL Investigation
  • Reviewed MicroStrategy generated SQL
  • Validated WHERE conditions
  • Reviewed join logic
  • Compared outputs against historical results

A filter condition excluded a subset of valid products after a recent business-rule change.

Root Cause
Business logic changed. Generated SQL still used the old filtering condition. Valid products were excluded before data reached reporting outputs.
Fix
  • Updated SQL logic
  • Validated output counts
  • Regenerated dump files
  • Retested VBA report
Result
  • Missing 350 units restored
  • Business validation passed
  • User confirmed final report accuracy
Key Lesson
User Report → Data Validation → Lineage Tracing → Root Cause → Fix → Business Confirmation
Actions

  • Located the affected function, recipe, query or source field

Validation

  • Confirmed the production result with users

Story 1 - Insurance Data Product Delivery (需求 → SDLC → UAT → Training）
核心問題
我如何由業務需求開始，完成一個保險數據產品 Prototype， 並經歷由需求分析、開發、測試、培訓到正式交付嘅完整流程？
背景
業務部門依賴分散嘅保險資料、人工輸入流程同 Excel 工作方式。 不同角色有不同需要： - Management 希望快速睇到整理好嘅資料同計算結果 - Operations Users 希望改善資料輸入流程 - Reporting Users 希望取得一致而可監控嘅結果 - Business Users 希望減少重複輸入同人手整理工作 呢個項目嘅目標係喺六個月合約期內建立一個可供業務試用嘅 Prototype。
當年實際做法
需求收集
  • 與不同部門及不同角色嘅 Business Users 開會
  • 了解現有工作流程、困難及期望結果
  • 區分資料輸入、計算、監控及報表需求
  • 將 User Requirements 轉化成一項項系統功能
  • 識別不同 User Requirements 之間有冇衝突
方案設計
  • 構思 Solution Blueprint
  • 將整個項目拆成較細嘅 Development Tasks
  • 評估每項功能嘅技術難度及所需時間
  • 考慮功能之間嘅依賴及衝突
  • 評估功能對 User Experience 嘅影響
Agile Delivery
開發部分功能 → 向 Manager 更新 → 向 Users 展示 → 收集 Feedback → 調整下一輪功能
測試與推出
收集 User Scenarios → 內部測試 → Pilot User Training → 試行 → 擴大 User Group → 正式交付
  • 向不同角色收集實際 Use Cases
  • 定義預期輸入及預期結果
  • 先進行內部測試
  • 邀請每個部門嘅 Pilot Users 參與 Training
  • 準備 PPT、初稿文件及操作示範
  • 試行後逐步擴大使用者範圍
  • 提供 Bug Fix、User Support 同後續 Enhancement
正確做法與可以修正嘅地方
當年方向正確嘅部分
  • 先理解 Business Problem，而唔係直接寫 Code
  • 與不同角色收集需求
  • 將 Requirements 拆成 Functions 同 Tasks
  • 評估需求衝突、可行性及交付時間
  • 採用 Iterative Delivery，而唔係一次過完成
  • 使用 Pilot Users 進行試行
  • 提供 Training、Documentation 及 Post-deployment Support
可以補強嘅正式 Deliverables
  • Project Scope：清楚定義 In Scope、Out of Scope 同目標
  • BRD / Requirement List：記錄 Business Requirements
  • Functional Specification：將需求轉成 Input、Logic、Output 同 Validation
  • Process Map：記錄 As-Is 同 To-Be Process
  • Acceptance Criteria：每項功能應該點樣先算完成
  • Requirement Traceability：需求、功能同測試案例之間嘅對應
  • UAT Sign-off：正式記錄 User 是否接受交付結果
待核實： 當年可能有 Requirement Notes、Blueprint、Task List、 Training Documents 同 Testing Scenarios， 但未確認有冇使用正式 BRD、Functional Specification、 Traceability Matrix 或 UAT Sign-off。
現代 Approach
Business Problem → User Stories → Acceptance Criteria → Prioritised Backlog → Version-controlled Development → Automated Testing → UAT → Controlled Release → Monitoring
  • 使用 Jira、Azure DevOps 或同類工具管理 Backlog
  • 使用 Git 管理 Code、Documentation 同版本
  • 將 Acceptance Criteria 同 Test Cases 連結
  • 建立 Development、UAT 同 Production 環境
  • 透過 CI/CD 控制測試及部署
  • Go-live 後監控 Error、Usage 同 User Feedback

Story 2 - Insurance Data Governance & SSOT （資料混亂 → 建立可信資料）
核心問題
我如何將分散喺不同檔案、系統輸出同人手報表嘅保險資料， 整理成一份統一、可信、可追蹤嘅資料集？
背景
資料分散喺 Master Tables、Transaction Records、 Recalculation Records、System Outputs 同 User-maintained Files。 不同來源使用不同格式同結構，部分資料由人手輸入。 同一個 Transaction 可能有多次處理或 Recalculation， 形成多條互相獨立嘅紀錄。 Business Users 難以判斷： - 邊條紀錄最早 - 邊條紀錄最新 - 中間發生過幾多次改動 - 累計金額係幾多 - 邊個結果應該用於 Reporting
當年實際做法
資料來源整理
  • 識別 Master Data、Transaction Data 同 Recalculation Data
  • 收集 Server Files、System Outputs 同 User-maintained Reports
  • 了解不同資料來源嘅用途同大致業務含義
  • 與 Users 核對資料及取得共識
資料處理
收集來源資料 → Preprocessing → 清洗人工輸入 → 統一格式 → Transaction Sequencing → Running Total → Central Dataset
  • 使用 VBA 收集不同來源檔案
  • 處理 Missing Data、格式差異同人手輸入問題
  • 統一欄位格式及資料結構
  • 建立 Transaction 嘅先後次序
  • 識別最新紀錄
  • 新增 Running Total 同 Cumulative Amount
  • 建立供 Prototype 同 Reporting 使用嘅中央資料集
成果
互相獨立嘅 Records → 完整 Transaction History → 最新狀態 → 累積金額 → 可信 Reporting Result
正確做法與可以修正嘅地方
當年方向正確嘅部分
  • 先整理資料，再開發 Prototype
  • 識別同整合多個資料來源
  • 處理人工輸入及格式不一致問題
  • 建立 Transaction Sequence 同 Derived Calculations
  • 建立中央可信資料集
  • 與 Business Users 核對結果
完整 SSOT 正常應補充嘅 Deliverables
  • Source Inventory：來源、用途、Owner、Refresh Frequency
  • Data Profiling Results：Null、Duplicate、格式同數據類型問題
  • Business Definitions：每個重要欄位同計算嘅業務定義
  • Data Quality Rules：Mandatory Fields、Uniqueness、Validity
  • Reconciliation Report：來源同 SSOT 嘅 Row Count 及 Amount 對數
  • Exception Log：記錄 Unmatched、Invalid 或 Conflicting Records
  • Data Dictionary：欄位名稱、定義、類型、來源同計算邏輯
  • Ownership Model：邊個維護 Source、Rules、Mappings 同 Exceptions
待核實： 當年確定有做收集、清洗、標準化、Transaction Sequencing、 Running Total 同 Central Dataset。 但未確認有冇正式建立 Source Inventory、Data Dictionary、 Exception Log、Reconciliation Report 同 Ownership Matrix。
現代 Approach
Raw Sources → Bronze / Raw Layer → Silver / Validated Layer → Business Rules → Gold / Curated Dataset → Reporting & Analytics
  • Raw Layer 保留完整原始資料及 Source Metadata
  • Validated Layer 處理 Schema、Null、Duplicate 同標準化
  • Curated Layer 套用 Business Rules、History 同 Reporting Logic
  • 使用 Data Catalogue 記錄 Definitions、Ownership 同 Lineage
  • 使用自動化 Data-quality Tests 驗證完整性、一致性同唯一性
  • 將 Exceptions 放入 Quarantine Table，而唔係靜靜刪除
  • 建立 Source-to-Target Reconciliation 同 Pipeline Monitoring
現代做法同當年核心概念一致： 都係將 Raw、混亂及不一致嘅資料， 逐步整理成乾淨、可信及可以供業務使用嘅資料產品。 最大分別係現代架構會將 Raw、Validated 同 Business-ready 資料分層管理，並加入更正式嘅 Lineage、Testing 同 Ownership。

我如何理解不同保險資料之間嘅關係， 並將不同來源整合成一致嘅資料結構？
背景
不同來源包含 Master Data、Customer-related Data、 Transaction Records 同 Recalculation Records。 問題唔只係欄位名稱唔同， 而係要理解每條 Record 代表咩、 邊啲 Records 屬於同一個 Transaction， 以及如何建立完整嘅 Transaction History。
當年實際做法
Practical Data Modelling
識別資料實體 → 確認 Business Keys → 理解 Relationships → 建立 Mappings → 設計 Join Logic → 套用 Business Rules → 建立 Reporting Dataset
  • 識別不同來源代表嘅 Business Objects
  • 確認可用於連結紀錄嘅 Business Keys
  • 判斷哪些 Records 屬於同一個 Transaction
  • 區分原始紀錄同後續 Recalculation Events
  • 建立 Source-to-Target Mapping
  • 標準化欄位名稱、格式同 Code Values
  • 設計 Master Data 同 Transaction Data 之間嘅 Join Logic
  • 建立 Transaction Sequence、Latest Record 同 Derived Fields
  • 驗證 Unmatched、Duplicate 或 Incomplete Records
呢個屬於 Practical Business Data Modelling。 當年未必有建立正式 Enterprise ERD， 但實際需要理解 Entities、Keys、Relationships、 Record Grain、Mappings 同 Join Logic。
正確做法與可以修正嘅地方
當年方向正確嘅部分
  • 先理解資料代表嘅業務對象，再進行整合
  • 識別 Business Keys 同 Record Relationships
  • 建立 Source-to-Target Mapping
  • 定義 Join、Sequence 同 Calculation Logic
  • 驗證 Unmatched 同 Duplicate Records
正確建模時應該明確記錄
  • Business Entities：每個主要資料對象係咩
  • Record Grain：每一行代表咩業務事件
  • Business Keys：點樣唯一識別同一個 Record 或 Event
  • Relationships：一對一、一對多或多對多
  • Cardinality：Join 後會唔會產生 Duplicate Records
  • Source-to-Target Rules：來源欄位點轉成 Target Fields
  • History Rules：點保存原始、修改及最新版本
  • Exception Rules：Unmatched Records 點處理
待核實： 目前可以確認做過 Practical Mapping、Relationships、 Transaction Sequencing 同 Central Dataset。 但確切 Business Keys、每個 Table 嘅 Record Grain、 Relationship Cardinality 同正式 Mapping Document， 仲需要根據舊檔案或記憶進一步核實。
現代 Approach
Conceptual Model → Logical Model → Physical Model → Transformation Models → Semantic Model
  • Conceptual Model：定義主要 Business Entities 同 Relationships
  • Logical Model：定義 Attributes、Keys、Grain 同 Cardinality
  • Physical Model：落實 Tables、Columns、Data Types 同 Constraints
  • Transformation Models：將 Raw Sources 轉成 Conformed Entities
  • Semantic Model：為 Reporting 同 Analytics 提供統一 Business Definitions
  • 建立 Data Contracts，控制 Schema、Required Fields 同 Change Rules
  • 使用 Version-controlled Mapping 同 Transformation Logic
  • 加入 Relationship、Uniqueness、Referential Integrity 同 Reconciliation Tests
能力總結

Story 4 - Insurance Data Product Pipeline & Automation
核心問題
我如何將分散嘅來源資料， 透過收集、清洗、整合、轉換、驗證同 Reporting， 變成一個可以持續俾 Business Users 使用嘅數據產品？
背景
Prototype 需要嘅唔只係最後一份 Report。 背後需要一條可重複執行嘅 Workflow， 將不同來源資料收集、處理、整合、計算、驗證， 再交付俾 Business Users。
當年實際做法
Historical Pipeline
Source Files → VBA Collection → Preprocessing → Power Query Integration → M Code Transformation → Business Rules → DAX Calculations → SSOT Dataset → Reporting → Business Users
實際工作
  • 使用 VBA 觸發及自動化 File Collection
  • 處理不完整、格式不一致同人手輸入嘅資料
  • 使用 Power Query 整合不同來源
  • 使用 M Code 處理 Standardisation 同 Transformation
  • 建立 Mapping、Join 同 Business-rule Logic
  • 使用 Calculated Fields 或 DAX 處理 Running Total 同報表計算
  • 建立中央 Dataset 供 Prototype 同 Reporting 使用
  • 自動化部分 Reporting 同 Output Distribution
  • 支援 Testing、UAT、Training、Deployment 同 User Support
Validation Flow
Input Validation → Transformation Validation → Mapping Validation → Calculation Validation → Output Reconciliation → User Validation
正確做法與可以修正嘅地方
當年方向正確嘅部分
  • 自動化 Source File Collection
  • 將 Collection、Transformation 同 Reporting 串成完整流程
  • 先建立統一資料，再進行 Calculation 同 Reporting
  • 對 Mapping、Calculation 同 Output 進行 Validation
  • 由 Prototype Delivery 延伸到 UAT、Training 同 Support
一條完整 Production Pipeline 應該補強
  • Raw Data Retention：保存未修改嘅來源資料
  • Incremental Loading：只載入新增或改動資料
  • Idempotency：同一批資料重跑唔應造成 Duplicate
  • Error Handling：失敗時要記錄、停止或隔離錯誤資料
  • Logging：記錄開始時間、完成時間、Row Count 同 Error
  • Restart / Recovery：Job 失敗後可以由指定位置重跑
  • Schema Validation：防止來源欄位改動破壞 Downstream
  • Automated Reconciliation：自動比較 Source 同 Output Totals
  • Version Control：管理 VBA、M Code、DAX 同 Documentation
  • Monitoring & Alerting：Pipeline 失敗或 Data-quality 異常時通知 Owner
待核實： 現有資料確認你參與咗 Collection、Preprocessing、 Transformation、Business Rules、Validation、Reporting 同 User Support。 但 Scheduling、Logging、Restart Handling、Version Control、 Automated Alerting 同正式 SLA 暫時未有足夠證據。
現代 Approach
Source Systems → Orchestrated Ingestion → Raw Storage → Validated Transformation → Business-rule Models → Curated SSOT → Semantic Layer → BI / Data Product → Monitoring
現代技術示例
  • Ingestion：Azure Data Factory、Fabric Data Factory 或同類 Orchestrator
  • Raw Storage：Data Lake、Lakehouse 或 Cloud Object Storage
  • Transformation：SQL、Spark、Databricks 或 dbt-style Models
  • Data Quality：Automated Schema、Null、Uniqueness 同 Reconciliation Tests
  • Curated Layer：Warehouse / Lakehouse Business-ready Tables
  • Semantic Layer：Power BI Semantic Model 或受控 Business Metrics
  • Delivery：Dashboard、Application、API 或 Scheduled Output
  • Operations：Monitoring、Alerting、Lineage、Logging 同 Controlled Deployment
新舊做法對照
VBA Collection → Managed Ingestion → Power Query / M → Version-controlled Transformation → DAX / Report Logic → Governed Semantic Layer
當年同現代做法嘅核心思想其實一致： Source Data → Integration → Transformation → Business Rules → Validation → Trusted Dataset → Business Delivery 現代做法主要增加可擴展性、版本控制、自動測試、 監控、Lineage 同部署管理。

End-to-End Machine Learning Decision Flow
1. Define the Problem
  • What business decision will the model support?
  • What is the target variable?
  • Classification, Regression, Clustering or Anomaly Detection?
  • What is the cost of False Positive and False Negative?
2. Understand the Data
Data Collection → Target Definition → EDA → Data Quality Checks
  • Check sample size, distributions and missing values
  • Check duplicates, outliers and inconsistent records
  • Check whether features would exist at prediction time
  • Remove data leakage before modelling
3. Decide the Validation Strategy
  • Random independent observations → Random or stratified split
  • Imbalanced classification → Stratified split to preserve class proportions
  • Time-dependent data → Chronological split or TimeSeriesSplit
  • Repeated customers, policies or entities → Group-based split to prevent leakage
Keep the final test set untouched until model selection and tuning are complete. Use cross-validation on the training data for more reliable model comparison.
4. Decide Train / Validation / Test Allocation
  • Larger dataset → smaller test proportion may still provide enough observations
  • Smaller dataset → use cross-validation to maximise training-data usage
  • Minority class → ensure validation and test sets contain enough positive cases
  • Set a random state when reproducible results are required
There is no universal best split ratio. The decision depends on dataset size, class distribution, grouping and time structure.
5. Build the Preprocessing Pipeline
Missing Values → Outliers → Encoding → Scaling → Feature Engineering → Feature Selection
Fit preprocessing steps using training data only, then apply the fitted transformations to validation and test data.
6. Check Class Imbalance
  • Inspect class counts and class proportions
  • Assess whether the minority class is the business-critical outcome
  • Do not rely on accuracy when the majority class dominates
Class-Imbalance Decision
  • Mild imbalance with sufficient minority observations → Start with stratified validation and suitable metrics
  • Misclassification costs differ → Use class weights or cost-sensitive learning
  • Minority class has too few training examples → Consider oversampling or SMOTE on training folds only
  • Majority class is extremely large → Consider careful undersampling
  • Operational workload matters → Tune the decision threshold according to investigation capacity
Never rebalance the complete dataset before splitting. Rebalancing must remain inside the training process to prevent leakage.
7. Establish a Baseline
Dummy Baseline → Simple Interpretable Model → Advanced Models
  • Classification → Majority-class or rule-based baseline
  • Regression → Mean or median prediction baseline
  • Start with Logistic or Linear Regression where applicable
  • Only keep complex models if they provide meaningful improvement
8. Train and Compare Models
  • Use the same cross-validation strategy for every candidate model
  • Compare mean performance and performance stability
  • Consider interpretability, latency and deployment constraints
9. Decide Whether to Tune
  • Baseline is weak → Recheck data quality, features and problem definition before tuning
  • Training score high, validation score low → Overfitting: simplify, regularise or obtain more data
  • Both scores low → Underfitting: improve features or use a more suitable model
  • Model is promising and stable → Tune hyperparameters using cross-validation
Hyperparameter tuning should improve a valid model. It should not be used to hide weak data or poor feature design.
10. Select Evaluation Metrics
  • Balanced classification → Accuracy, Precision, Recall and F1
  • Fraud / risk detection → Recall, Precision, F1, PR-AUC and Confusion Matrix
  • Ranking across thresholds → ROC-AUC or PR-AUC
  • Probability quality → Calibration and probability-based metrics
  • Regression → MAE, RMSE, MSE and R² according to business cost
11. Tune the Decision Threshold
  • Default 0.5 is not automatically the best business threshold
  • Lower threshold → usually more positives flagged and higher recall
  • Higher threshold → usually fewer alerts and higher precision
  • Select threshold using business cost, risk tolerance and review capacity
12. Final Model Decision
Technical Performance + Business Value + Interpretability + Operational Feasibility → Final Model
13. Final Test and Error Analysis
  • Evaluate once on the untouched test set
  • Review False Positives and False Negatives
  • Check performance across important customer or risk segments
  • Confirm whether the result meets the original business objective
14. Deployment and Monitoring
Model Output → Dashboard / API / Batch Process → Business Decision → Monitoring → Retraining
  • Monitor data quality and feature drift
  • Monitor prediction and business performance
  • Review threshold suitability
  • Retrain when data patterns or business requirements change
